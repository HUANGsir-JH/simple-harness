# TUI v3 全面替换计划

> 计划日期：2026-08-15  
> 目标分支：`feat/tui-v3`  
> 状态：已完成  
> 参考实现：`../claude-code-source-code/src/components`（Claude Code v2.1.88 的 React/Ink TUI）

## 1. 背景与目标

当前 `internal/ui/tui` 已具备完整的交互能力，包括流式输出、工具调用、审批、Ask、命令补全、会话切换、队列、Todo、Plan、Usage 与上下文压缩。但现有界面采用常驻顶栏、深色画布、完整 ASCII 面板、全屏居中弹窗和显式角色标题，信息密度偏低，视觉层级也与终端原生内容割裂。

TUI v3 将参考 Claude Code 的内容优先设计，用一套全新的布局与视觉语言全面替换现有呈现，同时保留已经稳定的 agent、session、controller、event bridge 和 middleware 协议。目标不是复刻 Ink 组件代码，而是将其交互原则映射到 Go/Bubble Tea：

- 消息流是第一视觉主体，减少永久占用屏幕的框架元素。
- 用户消息有清晰但克制的视觉锚点；助手回复保持适合长文阅读的开放布局。
- 工具调用默认压缩成单行活动记录，必要时展开详情。
- 输入框是界面唯一持续强调的控件，状态与快捷提示贴近输入上下文。
- 审批、Ask、选择器在当前内容区内展开，不再用大面积空白包围的全屏卡片。
- 宽屏、窄屏和低高度终端均保持可读，不允许边框、文字或状态互相覆盖。

## 2. 设计依据

从 Claude Code TUI 提炼以下可迁移原则：

1. **开放式消息流**：助手内容不包卡片；用户输入使用背景或边界建立区别，而不是重复显示大型角色标题。
2. **局部边界**：输入与权限区主要使用上边线或上下边线，避免四周盒子造成层层嵌套。
3. **渐进披露**：工具结果、thinking、命令详情默认摘要展示，用户主动展开时才占用更多高度。
4. **邻近反馈**：spinner、队列、Todo、权限选择与输入区相邻，状态出现在哪里就在哪里处理。
5. **低噪声状态**：模型、权限、effort、context 等信息放在短状态行中，只在有值时显示。
6. **键盘优先**：选择器使用方向键/`j`/`k`、Enter、Esc；审批选项保持单键决策，并在屏幕上明确标注。

## 3. 范围与边界

### 3.1 全面替换的内容

- `view.go` 中的颜色、排版、标题、消息、工具、输入、状态、Todo、队列、命令补全、空状态和 overlay 渲染。
- `interaction.go` 中与新布局相关的高度计算和响应式约束。
- `model.go` 中仅属于展示体验的状态文案、spinner 风格、placeholder 和必要交互细节。
- `popup.go` 中选择器的展示结构与选项说明。
- 与上述表现直接相关的 TUI 测试。

### 3.2 明确保留的边界

- `Controller` 的 session 生命周期、agent 启动/取消、事件桥和落盘行为。
- `events.Event`、`middleware.Approver`、`middleware.AskRequest` 等跨层协议。
- slash command 的业务语义与配置来源。
- transcript/history 加载、markdown 渲染和工具结果数据加工逻辑；允许为了新 UI 增补纯展示元数据，但不改变模型可见内容。
- `run` 非交互输出，不随 TUI v3 改动。

## 4. 信息架构

屏幕从上到下由五个弹性区域组成：

```text
  session / model                                  optional mode

  user prompt
  assistant response
  tool activity
  ...                                              scrollable

  contextual overlay / command suggestions         only when active
  todo / queued prompts                             only when present

  ── input mode ─────────────────────────────────────────────
  > composer
  ────────────────────────────────────────────────────────────
  activity or toast                    permission · effort · ctx
```

### 4.1 会话条

- 单行、无背景填充、无品牌横幅。
- 左侧显示 `Harness` 与当前模型；右侧显示会话名或“New session”。
- Plan 模式作为短促的强调标记，不长期使用大色块。
- 极窄终端只保留最重要信息，并用显示宽度安全截断。

### 4.2 消息流

- 用户消息：使用柔和底色或左侧强调，首行以 `>` 作为稳定识别符；多行内容统一缩进。
- 助手消息：开放排版，使用 `*`/活动 glyph 作为轻量锚点，不显示占空间的 `ASSISTANT` 大标题。
- 系统消息：单行通知语义；成功、错误、中性分别使用绿、红、灰，但不包框。
- thinking：折叠时为一行摘要；展开时使用弱化左边界与 dim 文本。
- 空状态：展示简洁品牌欢迎区、工作目录/会话提示和一条可行动的输入提示；首条消息后完全消失。

### 4.3 工具活动

- 头部采用 `·` 运行、`✓` 成功、`×` 失败状态标记，并显示人类可读动词与关键参数。
- 默认紧凑显示摘要，结果详情使用弱左边界承载。
- 可展开项明确显示 `ctrl+o` 等价提示不可行时，使用当前实际支持的 `Enter` 提示，避免展示无效快捷键。
- diff、错误和命令输出保留现有语义着色。

### 4.4 输入与辅助区

- 输入框改为仅上下边线的开放结构，提示符位于正文左侧。
- 聚焦时边线使用强调色；timeline 聚焦时降低亮度并显示简短状态。
- 输入区高度仍按内容在 1 到 5 行之间增长。
- command completion 紧贴输入框上方，选中项用反色/强调标记，未选项不铺满大背景。
- Todo 和 queue 使用紧凑列表，不再形成独立大面板；超出可见数量时汇总。
- 底部左侧只显示当前活动、toast 或 ready 状态之一，右侧按空间逐级收缩状态字段。

### 4.5 审批、Ask 与选择器

- overlay 仍保持互斥和 FIFO 安全语义，但展示改为“内联对话区”：顶部强调边线 + 标题 + 内容 + 操作项。
- 审批项显示为编号/快捷键清晰的三行选择，危险操作摘要必须换行可读。
- Ask 单选、多选与自定义输入沿用现有按键语义，选中态同时使用光标与 mark，不能只依赖颜色。
- selector 支持当前值标记、可见窗口和滚动位置提示；描述列在窄屏下自动折到下一行。
- 帮助界面在宽屏为双列，窄屏为单列，使用实际支持的命令与按键。

## 5. 视觉系统

- 使用 ANSI 256 色并优先适配深色终端，不绘制全屏背景色，尊重用户终端主题。
- 主强调色采用暖橙/珊瑚色，信息色使用青色；成功、警告、错误分别用绿、黄、红。避免现有青色单一主导。
- 文字分为 primary、secondary、muted 三层；所有关键状态除颜色外还必须有符号或文本标识。
- 仅使用圆角/细线 Unicode 边界；在终端能力不可知时确保去色后仍能理解。项目已允许终端 Unicode，且现有依赖能正确计算显示宽度。
- 所有宽度计算使用 `lipgloss.Width`/ANSI-aware 截断，不按字节长度排版。

## 6. 实施分解

### Phase A：主题与布局骨架

- 定义 v3 palette、语义 style、border 与 glyph。
- 重写 `View`、session bar、composer、footer 和 `layout()`。
- 加入窄屏降级策略与空状态。

### Phase B：消息流与工具活动

- 重写 user/assistant/system/stream/thinking 的渲染。
- 重写工具头部、摘要、展开详情与 diff 呈现。
- 保持 hit target 与实际渲染行严格对齐。

### Phase C：上下文辅助区与 overlays

- 重写 command completion、Todo、queue。
- 重写 approval、Ask、selector、help。
- 保持 overlay 互斥、审批不丢、Esc/Enter/Space 行为不变。

### Phase D：测试与收尾

- 更新旧视觉文本断言，新增宽屏、窄屏、低高度、长文本和 ANSI 宽度测试。
- 覆盖 running/ready/error/plan/queue/todo/approval/ask/selector/thinking/tool expanded 等状态。
- 格式化并执行 TUI 包测试、全量测试、`go vet`、构建。
- 用真实 PTY 或可复现终端捕获验证至少 120x36、80x24、48x18 三种尺寸。

## 7. 验收标准

1. 运行 `harness` 后看到的是全新 v3 界面，旧 `HARNESS` 顶栏、四边 ASCII composer、`ASSISTANT`/`YOU` 大标签和居中盒式 modal 不再出现。
2. 首屏、对话中、流式响应、工具运行/完成/失败、审批、Ask、选择器和帮助都有统一视觉语言。
3. 48 列宽终端不发生横向溢出；18 行高时输入区、footer 和至少一行 timeline 始终可见。
4. 中英文、长路径、长命令、ANSI markdown 和多行输入不会破坏宽度或 hit target。
5. 所有既有命令、队列、焦点切换、展开/折叠、中断、审批与 Ask 行为保持兼容。
6. `go test ./internal/ui/tui -count=1`、`go test ./... -count=1`、`go vet ./...`、`go build ./cmd/harness` 全部通过。

## 8. 风险与控制

- **Unicode 边界兼容性**：只使用常见 box-drawing 与状态字符；测试 ANSI strip 后语义，必要时集中定义 glyph 便于回退。
- **动态高度回归**：辅助区出现/消失会改变 viewport；每个状态变化后统一走 `layout + refresh`，并测试低高度。
- **命中区域错位**：消息 cell 的 hit range 继续由最终渲染高度计算，不维护第二套估算。
- **markdown 二次换行**：完成态 markdown 与流式纯文本分别处理，最终宽度只在一个层级约束。
- **旧测试绑定文案**：只更新视觉契约相关断言；controller、session 和安全语义测试不因换肤削弱。
- **参考代码许可证/可维护性**：仅采用设计原则，不复制 Claude Code 源码或品牌资产；实现保持项目原生 Go/Bubble Tea 风格。

## 9. 非目标

- 不新增图片、语音、IDE 集成、vim mode、远程会话、subagent 面板等当前 harness 不具备的功能。
- 不改变 provider、agent loop、工具 schema、权限决策或会话存储格式。
- 不把 TUI 改造成 Web UI，也不引入 React/Ink 运行时。

- 已完成 v3 主题、单行会话条、开放式消息流、上下边线 composer、紧凑 footer 和空状态。
- 已完成用户/助手/thinking/stream/system 消息、工具活动、diff、Todo、queue 与命令补全的统一呈现。
- 已完成 approval、Ask、selector、help 的底部内联 overlay；保留互斥、FIFO 与原有键盘语义。
- 已修复 overlay 覆盖历史消息的问题：弹层现在参与布局并压缩 timeline；工具展开显示完整格式化参数与结果；命令补全五行窗口跟随当前选择滚动；`/effort` 不再重复渲染说明。
- 已加入辅助区高度预算、overlay 裁剪、ANSI-aware 宽度控制和 48×18 密集状态回归测试。
