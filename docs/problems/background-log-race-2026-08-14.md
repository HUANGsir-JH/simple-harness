# 并发启动后台任务时日志文件分配竞态（.bg 共享/丢失/串扰）

> 记录日期：2026-08-14 ｜ 级别：中（并发场景数据损坏 + 通知路径失效）
> 关联：ADR-038（后台进程）、ADR-040（完成自动通知）、ADR-042（修复）、`internal/tools/background.go`
> 状态：✅ 已修复（2026-08-14，版本 0.11.1）

## 现象

**并发**（同一轮内并行发起多个 `background: true` 的 `shell_command` 调用）启动后台任务时：

1. **部分任务被分配 `.bg_<纳秒时间戳>.log` 共享日志**：返回给模型的通知路径不是 `<pid>.log`，而是临时文件路径 `.bg_1786693034388147000.log` 之类（存在两个任务拿到**完全相同** `.bg` 路径的情况）。
2. **`.bg` 文件在任务运行期间即不存在**：任务完成后（甚至运行期间）`read_file`/`ls` 均找不到该文件——通知里的日志路径**指向不存在的文件**，模型无法读取输出。
3. **独立日志内容串扰**：某个任务（拿到独立 `<pid>.log` 的那个）的日志中混入其他任务的输出行（如 `34934.log` 含 "R2-A(3s) 开始"，`35516.log` 含 "E2-B(8s) 完成"）。
4. **部分输出丢失**：被分配 `.bg` 的任务其输出行丢失（如 `R2-B` 的"开始"行、`R2-A` 的"完成"行均无处可寻）。

**单任务**（顺序启动）从未出现该问题（23295、24267、32583、35360 等均日志完整正确）。

## 复现

并发发起 2~4 个 `background: true` 的 shell_command（各含不同标识输出 + sleep 数秒），任务完成后：
- 对比各返回的日志路径：出现 `.bg_*.log` 即命中；
- `read_file` 该路径：文件不存在；
- 读取同批独立 `<pid>.log`：内容含其他任务输出（串扰）、缺本任务输出（丢失）。

## 代码定位

`internal/tools/background.go` `startBackground`（180-227 行）：

```go
// 临时名先开文件：Start 前必须打开文件才能重定向，而 PID 要 Start 后才有。
tmp := filepath.Join(dir, fmt.Sprintf(".bg_%d.log", time.Now().UnixNano()))   // :186
f, err := os.Create(tmp)
...
pid = cmd.Process.Pid
logPath = filepath.Join(dir, fmt.Sprintf("%d.log", pid))
if err := os.Rename(tmp, logPath); err != nil {
    logPath = tmp // 平台差异降级保留临时名；结果显式返回实际路径，模型不猜文件名
}
...
```

并发调用路径：`internal/agent/agent.go:315` `go func(c *messages.ToolCall)` —— **工具调用并行 goroutine 执行**，多个 `startBackground` 可同时运行。

### 竞态分析（已确认，2026-08-14 复现验证）

1. **临时文件名碰撞（根因，已实测确认）**：`time.Now().UnixNano()` 在多 goroutine 并发下返回相同值——本机实测连续调用 **93% 返回相同值**（墙上时钟 tick 粒度粗，非纳秒精度）、8 并发同刻放行 **7~8 个相同**；`os.Create` 对已存在文件不报错（O_CREATE|O_TRUNC），多个进程的 fd 指向**同一 inode**，且各自带独立偏移——输出在相同偏移互相覆盖，等长行**整体覆盖**（第 8 轮 V1/V2 起止行等长 → V1 两行被 V2 完全覆盖，日志看似"干净"实为整体丢失）。
2. **Rename 竞态（已确认）**：若 A 先 `os.Rename(.bg_X → pidA.log)` 成功，B 的 `os.Rename(.bg_X → pidB.log)` 因源不存在失败（ENOENT）→ 降级 `logPath = tmp` → **通知路径指向已不存在的 `.bg` 文件**；且 B 的 fd 仍指向已被改名（现为 pidA.log）的 inode → B 的输出串扰进 A 的日志。
3. **运行期间 `.bg` 即不存在（第 8 轮证据，已解释）**：与"rename 失败保留临时名"完全吻合——失败原因**恰是**对方已把共享文件 rename 走，降级保留的 `.bg` 名当时已不存在（并非"失败时 .bg 应残留"的直觉）。

## 修复记录（2026-08-14）

1. **临时文件名唯一化（根修）**：`startBackground` 改用 `os.CreateTemp(dir, ".bg_*.log")`——随机后缀 + O_EXCL 创建，撞名（EEXIST）自动换新文件，唯一性由内核保证而非时间戳概率，从构造上消除共享 inode。同源一并修复：`shell.go` 前台 `.fg_*.log`（超时转后台 rename 同源竞态）、`evict.go` `tool_*.txt`（并发 eviction 落盘时后写者 O_TRUNC 覆盖先写者）。
2. **Rename 降级语义保留但已安全**：tmp 由 O_EXCL 唯一创建、他人不可见也不可改，降级后的通知路径必然存在（注释同步说明与旧实现差异）。
3. **并发回归测试**：`TestShellCommandBackgroundConcurrentUniqueLogs`（12 轮 × 8 任务，屏障同刻放行直调 `startBackground`；断言：路径全部唯一且为 `<pid>.log`、文件可读、内容仅含本任务输出、目录无 `.bg` 残留）——修复前一次运行即复现全部四症状（round 1 task 6 得 `.bg` 路径、task 4 日志串入 task 6 输出、task 4 本任务输出整体丢失、task 6 通知路径不存在），修复后 3 连跑全绿。
4. **模型侧规避**：不再需要（工具侧已根治）。

### 验证

`go build/vet/test ./...` 全绿；`go test -race ./internal/tools/` 绿；linux/windows/darwin 交叉编译绿。版本 0.11.1。

## 影响

- **模型侧**：通知中的日志路径不可读（read_file 失败），后台任务输出丢失，无法轮询/审计；多任务并发时输出互相污染，模型可能把 B 的输出当作 A 的（信息误导）。
- **用户侧**：并发起多个后台任务（多路下载、并行构建等）是常见用法，数据损坏概率高（62%）。
- **通知链路本身正常**：并发任务全部收到完成通知（exit 0、无遗漏、无重复），问题仅在日志文件分配。

## 建议修复方向（2026-08-14 评估采纳结果）

1. **临时文件名加唯一性**：✅ 采纳，且优于原案——直接 `os.CreateTemp`（随机后缀 + O_EXCL），无需手工组合 pid/计数器/随机串。
2. **Rename 失败重试/回退**：不采纳（无需）——临时名唯一化后 rename 失败只剩平台差异/异常文件系统场景，降级保留的 tmp 必然存在，语义安全。
3. **并发回归测试**：✅ 已补（`TestShellCommandBackgroundConcurrentUniqueLogs`，见修复记录）。
4. **短期规避（模型侧）**：不再需要（工具侧已根治）。
