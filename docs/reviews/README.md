## 阅读顺序建议

报告分三层，可按需取用：

1. **已验证缺陷（01~10）** — 均有探针证据，可直接排期修复
2. **设计层面** — 只有一条（审批授权粒度）。与其余缺陷的区别是：补实现补不出来，
   需改`Decide` 的输入契约，且与规划中的 workspace 耦合
3. **可维护性 / 其余已核实的问题** — 不影响正确性，按余力处理

## 命名约定

`<类型>-review-<YYYY-MM-DD>.<ext>`，例如 `architecture-review-2026-08-10.html`、
`security-review-2026-09-01.md`。同一天同类型多份时追加 `-2`。

## 阅读约定

- 报告中的缺陷编号（第 01~10 项）仅在**该份报告内**有效，不跨报告延续
- 标注"已用探针证实"的结论均可复现；探针本身不入库（跑完即删，避免污染测试套件）
- 报告是**某一时点的快照**：修复后不改报告，而是在新报告中记录状态变化。
  引用旧报告结论前先确认对应代码是否已变更

## 与ADR 的关系

审查发现的问题若引出设计变更，决策写入 `docs/tasks/DECISIONS.md`（ADR），
报告只负责陈述问题与证据，不替代 ADR 做决策记录。
